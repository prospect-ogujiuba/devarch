# GLPI AD, inventory and email intake runbook

**Status:** Implementation baseline  
**Audience:** Systems administrators and help-desk administrators  
**Applies to:** GLPI 11, Active Directory, Microsoft Entra ID, Microsoft 365  
**Owner:** IT

## 1. Purpose

This runbook configures GLPI so that:

- Active Directory (AD) or Microsoft Entra ID remains authoritative for users and groups;
- GLPI Agent supplies current computer hardware and software inventory;
- GLPI Inventory optionally discovers network devices and printers; and
- email sent to `support@fluidhose.com` automatically creates and updates GLPI tickets.

Do not manually maintain identity or computer data in GLPI when an authoritative integration supplies it.

## 2. System ownership

| Information | Authoritative system |
|---|---|
| Login, name, email, department and account status | AD or Entra ID |
| Application access entitlement | AD or Entra security groups |
| Computer hardware, serial numbers, installed software and network details | GLPI Agent |
| Printers, switches and other SNMP-capable equipment | GLPI Inventory |
| Asset assignments, contracts, lifecycle and financial information | GLPI |
| Incidents, service requests, communication and SLAs | GLPI |
| Support mailbox | Microsoft 365 or the approved mail provider |

AD computer objects are not an inventory replacement. They normally identify only the domain object and do not provide dependable hardware, software, disk, serial-number or peripheral data.

## 3. Target architecture

```text
Active Directory -- LDAPS --> GLPI users and groups
       |
       +-- Group Policy --> GLPI Agent on Windows computers
                                  |
                                  +-- HTTPS inventory --> GLPI assets

Microsoft Entra ID -- SCIM --> GLPI users and groups       (cloud-only option)
Microsoft Entra ID -- OAuth SSO --> GLPI authentication    (cloud-only option)

support@fluidhose.com -- OAuth IMAP --> GLPI receiver --> ticket
GLPI -- authenticated SMTP --> requester and technician notifications
```

Use either the LDAPS identity path or the Entra SCIM/OAuth path as the primary provisioning design. Do not provision the same users independently through both paths without documented matching and conflict rules.

## 4. Configure identity provisioning

### 4.1 Select one authoritative path

Determine the tenant topology before configuring GLPI:

| Tenant topology | GLPI integration | Authoritative identity chain |
|---|---|---|
| Cloud-only Microsoft 365 | Entra SCIM for provisioning plus OAuth SSO for sign-in | Entra ID → GLPI |
| Hybrid, with users created in on-premises AD and synchronized by Entra Connect | Prefer one deliberate interface: Entra SCIM/OAuth for an internet-accessible GLPI, or LDAPS when GLPI has secure domain-controller connectivity | AD → Entra ID → GLPI, or AD → GLPI |
| On-premises AD without Entra provisioning | LDAPS | AD → GLPI |

Do not point a cloud-only tenant at LDAP. Do not provision the same users independently through SCIM and LDAP. Record the chosen path, owner and stable matching attribute before importing anyone.

For the Entra path, GLPI must have a stable production HTTPS hostname reachable by Microsoft's provisioning service and by users. The local `glpi.test` endpoint is not suitable. The current repository deployment has no plugins installed.

Use only the official GLPI Network packages: [**SCIM** (`scim`)](https://help.glpi-project.org/faq/plugins/scim) for provisioning and [**OAuth SSO** (`oauthsso`)](https://help.glpi-project.org/doc-plugins/fr/plugin-glpi-network/oauthsso) for sign-in. Install them through GLPI's authenticated in-application Marketplace connected to the organisation's GLPI Network account. Independently verify each package against those vendor pages and capture the package key, displayed GLPI Network/Teclib publisher, exact version, GLPI/PHP compatibility, subscription entitlement and release notes in the change record. Record the Marketplace transaction/download time and package hash when the Marketplace supplies one. If a package must be side-loaded, stop unless Teclib provides a documented HTTPS download plus a checksum or signature that can be verified out of band. Do not install a similarly named archive from search results or an unverified repository.

For this GLPI 11 deployment, the Marketplace must explicitly offer a GLPI 11-compatible release; the [OAuth SSO vendor documentation](https://help.glpi-project.org/doc-plugins/fr/plugin-glpi-network/oauthsso) requires a GLPI Network BASIC-or-higher entitlement for self-hosted use. Plugin availability, compatibility, provenance and entitlement are production gates, not assumptions. After installing in a non-production copy or maintenance window, run the plugin's database migration, confirm its status is **Enabled**, and record the endpoint/redirect URI generated by that installed version before creating any Entra application.

Separate duties and permissions:

| Duty | Least-privilege starting point | Permission boundary |
|---|---|---|
| Create/configure the Enterprise Application and SCIM provisioning job | **Application Administrator** or **Cloud Application Administrator** during setup | Configure provisioning URL/token, attribute mappings, assignments and pilot scope; Entra is the SCIM client, so do not add broad Graph application permissions to GLPI for provisioning |
| Create/configure the OAuth SSO app registration | **Application Administrator** or **Cloud Application Administrator** during setup | Add only the installed plugin's exact redirect URI and delegated `openid`, `profile`, `email`, `offline_access` and `User.Read` scopes documented for Entra SSO; no `User.ReadWrite.All` or `Group.ReadWrite.All` |
| Grant tenant consent | Authorized consent administrator under tenant policy | Review the final permission manifest; consent is separate from application construction and is not automatically implied by the Application Administrator role |
| Operate the configured application | Named Enterprise Application/App Registration Owner where tenant policy permits | Review logs, rotate credentials and change pilot assignments for only this application; no tenant-wide directory administration |
| Deploy GLPI Agent | Intune **Application Manager** or scoped MSP/RMM operator | Endpoint application packaging/assignment only; this grants no identity-application or consent authority |

Use a pilot security group such as `APP-GLPI-Users`. Never assign all tenant users during initial configuration. Store SCIM bearer tokens and OAuth client credentials in the approved secret manager, not in this repository or screenshots.

### 4.2 Reconcile existing GLPI users before provisioning

Existing application-local accounts may already own tickets, assets or history. Bulk provisioning before reconciliation can create duplicate people and split ownership.

1. Back up GLPI and export existing users with GLPI ID, login, email, authentication source, active state, entity and profiles.
2. Export the approved Entra or AD pilot population with user principal name, primary email, Entra object ID or AD `objectGUID`, and enabled state.
3. Apply this authoritative matching precedence: first, one existing GLPI user already carrying the same persisted Entra-object-ID/SCIM-`externalId` correlation (or AD `objectGUID` for LDAPS); second, one manually approved existing GLPI user whose unique normalized UPN/primary email is being adopted during the controlled bootstrap. GLPI ID remains the record that must be preserved. Never replace a stable external-ID match with an email match.
4. Fail closed when the stable identifier maps to more than one GLPI user, UPN/email is absent or non-unique, stable-ID and email candidates disagree, the source is a guest/shared/service identity outside scope, or the installed plugin cannot demonstrate the intended mapping. Do not auto-create, merge, relink or deactivate any conflicting record; quarantine the provisioning event for manual resolution.
5. Prove with one disposable or backed-up pilot that the installed plugin's documented matching/adoption behavior attaches the external identifier to the existing GLPI user ID. If the plugin version cannot adopt the existing record without creating a second user, stop and obtain a vendor-supported migration procedure; do not provision around the duplicate and do not update authentication tables directly.
6. Confirm that the same GLPI user ID retains its tickets, assets, requester history, entity and intended profile after directory sign-in.
7. Record approved matches and exceptions, then repeat for a small pilot group before enabling broader provisioning.
8. Stop any legacy importer from overwriting directory-owned login, name, email, department or active state.

Display name alone is never a valid matching key. Keep the local `glpi` break-glass administrator outside SCIM/LDAP lifecycle control and test it before every authentication change. Complete and rehearse section 4.5 before enabling any recurring provisioning or SSO assignment.

### 4.3 Entra SCIM provisioning and OAuth SSO

Use this path for cloud-only Microsoft 365 and, by deliberate design, for hybrid tenants that want Entra to be GLPI's integration boundary.

#### 4.3.1 Provision users and groups with SCIM

1. Install and enable the official GLPI Network Marketplace **SCIM** (`scim`) release whose Marketplace metadata explicitly supports the installed GLPI 11/PHP versions; record the exact installed version and release notes.
2. In GLPI, create the SCIM endpoint/token according to that installed version's guidance. Copy the secret directly into the approved secret manager and Entra; do not write it into a ticket or repository file.
3. In Entra, create or select the GLPI Enterprise Application and set provisioning mode to **Automatic**.
4. Enter the GLPI SCIM tenant URL and secret token, then run **Test Connection**.
5. Review attribute mappings. Preserve the plugin defaults unless a documented business mapping requires a change; ensure UPN/login, primary email, given name, surname, active state and stable directory identifier have unambiguous targets.
6. Set provisioning scope to **Sync only assigned users and groups** and assign only `APP-GLPI-Users` plus the approved role groups.
7. Use **Provision on demand** for one reconciled pilot user. Confirm create/update behavior, group membership, entity/profile rules and ownership retention in GLPI.
8. Test a name change, group removal and disabled pilot account. Disable rather than delete historical GLPI users unless the approved retention policy explicitly says otherwise.
9. Enable the provisioning cycle only after the pilot results and Entra provisioning logs are reviewed.

SCIM provisions lifecycle and attributes; it does not synchronize Microsoft passwords and does not by itself let a user sign in.

#### 4.3.2 Authenticate with Microsoft using OAuth SSO

1. Install and enable the official GLPI Network Marketplace **OAuth SSO** (`oauthsso`) release whose Marketplace metadata explicitly supports the installed GLPI 11/PHP versions; record the exact installed version and confirm the required GLPI Network entitlement.
2. From GLPI, copy the exact production redirect URI displayed by that installed version.
3. Create the Entra app registration/enterprise application using the tenant-specific configuration and exact redirect URI. Do not use `glpi.test`.
4. Configure only the claims and delegated/API permissions required by the installed plugin version. Have the tenant administrator review any admin-consent request before granting it.
5. Store the client credential in the approved secret manager and GLPI's protected configuration. Record its owner and expiry, and create a rotation reminder.
6. Configure GLPI's Entra tenant/issuer, client ID and secret. When SCIM owns user attributes, set OAuth SSO **Fetch information from user profile** to **No** so sign-in does not overwrite SCIM-managed fields.
7. Create GLPI authorization-assignment rules that map only approved Entra users/groups or application roles to the correct entity and profile. SSO success alone must not grant administrative access.
8. Test in a private browser with one reconciled user, one new pilot user, a user outside the pilot group and the local break-glass administrator.
9. Make Microsoft sign-in visible to the pilot group only. Do not enforce or broaden SSO until provisioning, authorization, logout, group removal and break-glass tests pass.

OAuth SSO authenticates users but does not replace SCIM provisioning.

### 4.4 On-premises or hybrid AD through LDAPS

Use LDAPS only when AD is authoritative and GLPI has secure DNS/network access to redundant domain controllers. In GLPI, open **Setup → Authentication → LDAP directories**, select the Active Directory preset and configure:

| Setting | Recommended value |
|---|---|
| Server | Domain-controller FQDN; configure redundancy where supported |
| Port | `636` |
| Encryption | LDAPS/TLS with certificate validation |
| Base DN | Organisation's approved AD search root |
| Bind DN | Dedicated read-only GLPI LDAP service account |
| Login field | `userPrincipalName` for this Microsoft 365-aligned pilot; an existing `sAMAccountName` deployment must be reconciled and migrated under a separate approved change before import |
| Synchronization field | `objectGUID`, chosen because Microsoft defines it as the AD object's stable unique identifier; subject to the installed GLPI version's LDAP implementation |
| Email | `mail` |
| First name | `givenName` |
| Last name | `sn` |
| User's groups | `memberOf` |
| Group members | `member` |
| Group name | `cn` |

Use this enabled-person filter:

```ldap
(&(objectClass=user)(objectCategory=person)(!(userAccountControl:1.2.840.113556.1.4.803:=2)))
```

For a controlled rollout, add an `APP-GLPI-Users` membership condition using the group's actual distinguished name.

The selection combines GLPI's documented [LDAP synchronization-field configuration](https://help.glpi-project.org/documentation/modules/configuration/authentication/ldap) with Microsoft's definition of [`objectGUID` as the object GUID](https://learn.microsoft.com/en-us/windows/win32/adschema/a-objectguid). Before import, validate the exact installed GLPI core version and LDAP synchronization implementation: confirm the GLPI 11 UI accepts `objectGUID` as the synchronization field, record the installed version, selected field and test result in the change record, then pilot one user. Record that user's GLPI ID and `objectGUID`, rename/change the AD user's UPN, synchronize again and prove GLPI updates the same user ID. No import may proceed until this installed-version validation passes. Stop if the installed core behaves differently; do not substitute email or display name silently.

Implementation sequence:

1. Confirm the GLPI container trusts the AD certificate authority.
2. Confirm DNS resolution and TCP 636 connectivity from GLPI to at least two domain controllers.
3. Create a dedicated read-only bind account; deny interactive sign-in and store its password in the approved secret manager.
4. Test the LDAP connection.
5. Import the approved GLPI access groups.
6. Reconcile and import one pilot user before bulk synchronization.
7. Map `APP-GLPI-Users` to Self-Service, `APP-GLPI-Technicians` to Technician and `APP-GLPI-Admins` to the approved administrative profile.
8. Configure disabled or removed directory users to be disabled rather than deleted in GLPI.
9. Schedule GLPI's LDAP user synchronization and monitor failures.
10. Test certificate failure, bind-account rotation, group removal and the local GLPI break-glass administrator.

### 4.5 Identity rollback and recovery test

Before enabling SCIM, OAuth SSO or LDAPS, record the current authentication sources, authorization rules, plugin versions/configuration, Entra assignments and attribute mappings; export the affected GLPI users; and take a restorable database/application backup. Never export secret values into the change record.

#### 4.5.1 Queue-drain barrier for every identity path

Rollback is not complete merely because a configuration toggle is off. Establish a barrier timestamp and record the last successful/failed event ID before changing the integration.

- **SCIM:** stop the Entra provisioning job, remove pilot assignments and disable provision-on-demand use. Export Entra provisioning/audit logs from before and after the barrier, identify retries/quarantined events and require every queued/running request already sent to GLPI to appear as succeeded, failed, canceled or quarantined; queued/running counts must be zero. Reconcile every post-barrier user/group change against the GLPI baseline; if any change arrives after the first comparison, repeat the drain and comparison.
- **LDAPS:** suspend both GLPI's automatic action and every host/container scheduler invocation. Inventory every queued scheduler/import operation and require each one to be canceled or reach a recorded terminal state (`succeeded`, `failed` or `quarantined`); pending/running counts must be zero. Resolve/account for bind failures, scheduler retries and pending directory updates in the GLPI logs. Record the last completed synchronization ID/time and prove no later user/profile/entity update appears after one full former interval.
- **Evidence:** preserve bounded logs/event IDs, the pre/post user export and the exception list in the approved change record without secrets. A queued or ambiguous event blocks rollback completion and wider rollout.

Rollback order for an Entra pilot:

1. Stop Entra provisioning and remove the pilot group assignment so no queued lifecycle change races the rollback. Confirm the provisioning job is stopped before continuing.
2. Keep the local break-glass session open and prove a new local break-glass login works.
3. Disable the Microsoft sign-in button/application in GLPI **and** set the Entra Enterprise Application to block user sign-in; then remove every pilot user/group assignment. Terminate all pilot users' active GLPI sessions so an existing application session cannot mask rollback failure. Do not delete the app registration while it is still the only path to a user.
4. After confirming that the app registration is dedicated to GLPI and no other environment depends on it, remove the GLPI production redirect URI from **Authentication**, remove the GLPI delegated API-permission configuration from **API permissions**, and revoke both user consent and any admin-consent/service-principal grants. Removing a configured permission and revoking its existing grant are separate checks; complete both.
5. Revoke every pilot user's Entra refresh/sign-in sessions using the tenant's approved procedure. Inventory all client secrets/certificates ever issued for the pilot, delete every retired credential including superseded secrets, revoke the SCIM token, and remove the credentials from GLPI after the integration is disabled.
6. Restore the recorded GLPI authorization rules and pre-change plugin configuration. Preserve existing GLPI user IDs and ownership history. Disable incorrectly provisioned pilot users; do not delete or merge them until ticket/asset ownership has been audited.
7. Compare the post-rollback user export with the baseline and verify local login, ticket ownership, entity/profile assignments and absence of new Entra provisioning events. In a private browser, verify the GLPI Microsoft sign-in entry is absent/disabled; the removed redirect URI is absent from Entra and an authorization attempt against it is rejected; an old refresh token and every retired client secret cannot obtain a token; and the removed consent/grant cannot authorize the GLPI delegated sign-in flow.
8. Restore the database/application backup only inside an approved rollback window when post-backup GLPI changes have been accounted for; a database restore is not the default identity rollback.

For LDAPS rollback:

1. Suspend the scheduled `glpi:ldap:synchronize_users` action and any host/container scheduler that invokes it. Confirm no synchronization/import process is running; allow an active supported transaction to finish, or stop it only through GLPI's supported scheduler controls.
2. Capture the final LDAP/import log and user export, then wait until GLPI shows zero pending/running directory import or synchronization work and every previously queued operation has a recorded canceled/succeeded/failed/quarantined terminal result.
3. Prove a new break-glass login, disable the LDAP directory configuration and restore the prior authentication/authorization rules.
4. Revoke or rotate the bind credential and confirm the retired credential cannot bind.
5. Wait at least one full former synchronization interval and verify no further directory updates, user disables, profile/entity changes or duplicate users occur; then compare ownership and access with the baseline.

Document the tested recovery result before expanding beyond the pilot.

## 5. Configure computer and equipment inventory

### 5.1 Native computer inventory

Deploy GLPI Agent to managed workstations and servers. Configure its server target as:

```text
https://<glpi-host>/front/inventory.php
```

Use HTTPS with a certificate trusted by each endpoint. In this repository's local environment, replace `<glpi-host>` with the reachable GLPI hostname; do not deploy the development-only `.test` hostname to production clients.

#### 5.1.1 Deployment authority and prerequisites

Access to Entra ID alone does not grant software-deployment rights. Choose one managed channel:

- **Microsoft Intune:** target computers must be Intune-enrolled. The operator needs an Intune role with the required **Mobile apps** create, read, update and assign permissions; the built-in **Application Manager** role is the usual least-privilege starting point. Confirm applicable scope groups, scope tags and Multi Admin Approval policy.
- **MSP/RMM:** give the MSP the approved installer, silent-install command, production inventory URL, pilot group, detection rule and rollback criteria. Do not provide a GLPI administrator password; endpoint inventory submission does not require one.
- **Group Policy:** use only for computers managed by reachable on-premises AD when the software-distribution and rollback process is already supported.

Before packaging the agent:

1. Export any existing GLPI Agent version, server target, task schedule and local configuration for pilot devices so a superseded installation can be restored exactly.
2. Replace `<glpi-host>` with a stable production hostname reachable from managed computers. Never deploy `glpi.test`.
3. Use a publicly trusted or organisation-trusted HTTPS certificate and test the full chain from a pilot computer.
4. Back up GLPI, test the local break-glass account and review import/linking rules.
5. Download the current supported Windows MSI from the official GLPI Agent release source. Record its version and SHA-256 checksum, and verify its digital signature before the MSP or Intune upload.
6. Create a pilot device group containing two or three representative computers, including a laptop with a dock/display and a computer using the normal printer configuration.

#### 5.1.2 Windows package and pilot assignment

Use the vendor MSI as a Windows Win32 application or the MSP's managed package. Adapt the following silent install to the approved MSI filename:

```powershell
msiexec.exe /i "GLPI-Agent-<version>-x64.msi" /qn /norestart SERVER="https://<glpi-host>/front/inventory.php" RUNNOW=1
```

Use the corresponding silent uninstall command based on the MSI product code recorded during packaging:

```powershell
msiexec.exe /x "{MSI-PRODUCT-CODE}" /qn /norestart
```

Package requirements:

- install in the system/device context, not with an end user's privileges;
- require supported 64-bit Windows and sufficient free space;
- use the MSI product code and installed version for detection rather than a transient process;
- configure supersedence or an MSP upgrade policy for later agent versions;
- return the MSI exit code to the management platform and treat `3010` as success with restart required where applicable;
- do not embed credentials, tokens or private certificates in commands, scripts or packages; and
- assign as **Required** only to the pilot device group initially.

After installation, confirm the GLPI Agent service is running and trigger one inventory. Allow for the server's inventory-processing interval before diagnosing a missing asset.

In GLPI, configure inventory rules to:

- assign imported computers to the correct entity;
- link inventory to an existing asset rather than creating duplicates;
- use stable identifiers such as UUID and serial number;
- associate the last logged-in directory username with the matching GLPI user where appropriate; and
- reject or quarantine inventory that cannot be assigned safely.

Do not use computer name as the sole matching identifier because names can be reused.

### 5.2 Asset data populated by the agent

A standard endpoint inventory primarily creates or updates **Assets → Computers**. The exact fields depend on the operating system, available hardware interfaces and GLPI import rules.

| GLPI area | Data normally supplied by GLPI Agent |
|---|---|
| Computer identity | Hostname, manufacturer, model, serial number and UUID |
| Components | Processor, memory, motherboard/BIOS, disks and storage controllers, graphics, sound, batteries and network adapters when detectable |
| Operating system | Name, edition, version, architecture, kernel and installation details when exposed by the OS |
| Network | Interfaces, MAC addresses, IP addresses and network ports |
| Software | Detected installed applications, versions and installation associations; this is installation evidence, not software-license entitlement |
| Connected devices | Monitors, locally visible printers and peripherals; these may be linked or created as separate **Assets → Monitors**, **Printers** or **Devices** records according to inventory rules |
| User and inventory metadata | Last logged-in username when detectable, agent version, last contact and last inventory update |

The endpoint agent does **not** authoritatively supply business and lifecycle data. Maintain the following in GLPI or populate them through approved rules and integrations:

- entity, location, assigned user or department;
- asset status, lifecycle state and internal asset/inventory tag;
- supplier, purchase date, purchase price and warranty details;
- contracts, budgets, depreciation and other financial information; and
- purchased software licences and entitlement counts.

Lock intentionally maintained manual fields where appropriate, and test that subsequent inventories do not overwrite them.

### 5.3 Network devices and printers

Endpoint inventory alone does not fully inventory switches, routers, firewalls, wireless access points or network printers. Install and enable **GLPI Inventory** when network discovery, SNMP inventory, ESX inventory, data collection or remote deployment is required. With supported devices and SNMP access, it can populate **Assets → Network equipment** and **Assets → Printers**, including network identity, ports and device-specific counters or consumable data where available. Use a least-privilege SNMP credential, restrict discovery ranges and pilot each range before scheduling broad scans.

### 5.4 Pilot inventory acceptance tests

For each pilot computer, record its hostname, serial number, physically connected monitors, installed printers and primary user before deployment. Then verify that:

- one pilot computer appears only once;
- manufacturer, model, UUID, serial number, disks, memory, operating system and installed software are populated;
- a renamed computer updates the existing asset;
- the correct user and entity are assigned;
- an agent rerun updates automatic fields without overwriting intentionally locked manual fields;
- each directly connected monitor is detected when its EDID is exposed, with manufacturer, model and serial number where the display and connection provide them;
- each locally installed printer or print queue is reported and linked as expected; and
- decommissioning behavior is documented and tested.

Monitor and printer discovery is best-effort. Docks, KVMs, display adapters, generic drivers, disconnected or sleeping displays, shared queues and some USB devices may omit identity or serial data. A printer reported by a workstation is not a substitute for SNMP inventory: use GLPI Inventory network discovery/SNMP for page counters, consumables, ports and network-printer details.

Compare GLPI with the physical pilot workstation and record unexplained differences. Do not expand the deployment until duplicate handling, field locking, HTTPS communication and the expected monitor/printer coverage pass.

### 5.5 Expansion, monitoring and rollback

Expand in rings: IT, one representative department, then remaining managed computers. For each ring, monitor installation failures, stale agents, duplicate computers, unexpected entity/profile assignments and inventory-processing errors.

Pause expansion when the duplicate rate is non-zero, the inventory endpoint is unavailable, TLS validation fails or material hardware data is missing. Correct the package or server-side rule, rerun the pilot and reapprove expansion.

To roll back endpoint deployment, apply a queue-drain barrier: rollback is incomplete until every Intune/MSP/RMM management command and every local/server inventory submission is canceled or reaches a recorded terminal state.

1. Freeze package changes for the pilot in every active deployment channel. Remove/exclude the **Required** assignment, force a management sync, inspect both Intune and MSP/RMM device job queues, cancel every pending install/uninstall/retry action, and wait for any already-running management job to reach a recorded terminal state before reconciling the device.
2. Stop the GLPI Agent service/tasks to prevent a new local submission and confirm no agent process or outbound inventory connection remains. Then issue the managed MSI uninstall. Verify that the platform reports success, the MSI detection rule no longer matches, the service/process and local scheduled task are absent, and the agent's local pending/spool queue is absent or empty. Do not manually delete an in-flight payload; account for it on the server.
3. If this deployment replaced a prior supported agent or server target, reinstall the recorded prior version/configuration and verify its service, schedule and destination. Otherwise confirm no agent remains.
4. In GLPI, inventory every queued, retried, processing and quarantined submission associated with the pilot. Cancel it through supported controls or require it to reach a recorded terminal state (`processed`, `failed`, `canceled` or deliberately `quarantined` with an owner/disposition); pending/running/retry counts must be zero before rollback completion. When supported, temporarily quarantine the pilot UUID/serial in the import rules while queues drain. Record the asset ID and last-contact timestamp, wait at least one full former agent scheduling interval plus the server processing interval, and confirm no later contact, asset recreation, duplicate or automatic-field mutation occurs before removing the temporary quarantine.
5. Preserve the existing GLPI computer/user ownership and inventory history. Removing an agent must not delete its asset; apply the approved retirement/status process and quarantine duplicates rather than merging or deleting them blindly.
6. Re-run the physical asset comparison if the previous agent/configuration is restored.

## 6. Configure `support@fluidhose.com` email intake

### 6.1 Mailbox preparation

Create `support@fluidhose.com` as a dedicated mailbox rather than relying only on a distribution list. Preserve the original sender address and normal internet message headers. Do not configure an automatic reply that loops back into GLPI.

For Microsoft 365:

1. Install only the official [`pluginsGLPI/oauthimap`](https://github.com/pluginsGLPI/oauthimap) **OAuth IMAP** (`oauthimap`) release whose Marketplace metadata explicitly supports the installed GLPI 11/PHP versions; record the exact version and provenance. The official [plugin manifest](https://github.com/pluginsGLPI/oauthimap/blob/main/oauthimap.xml) declares the 1.5.x line compatible with GLPI 11, but the Marketplace result at deployment time remains authoritative.
2. Create a dedicated Entra app registration using the exact callback URL displayed by the installed plugin.
3. Use the plugin's delegated authorization flow for the dedicated collector identity. Grant only the documented OpenID/profile scopes and delegated `IMAP.AccessAsUser.All` plus `offline_access` described by [Microsoft's Exchange Online OAuth guidance](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth); do not grant `IMAP.AccessAsApp`, broad Microsoft Graph application permissions or tenant-wide mailbox access for this delegated design.
4. Limit the collector identity to `support@fluidhose.com`. If it is a shared mailbox, grant only the required Exchange **Full Access** delegation to the dedicated identity; do not grant unrelated mailbox access.
5. Complete administrator consent only when tenant policy requires it and after the permission list is reviewed. Create the client credential in the approved secret manager, record its owner/expiry and test rotation; do not store it in this repository.
6. Configure outbound mail separately. If GLPI uses OAuth SMTP, grant delegated `SMTP.Send` only to the dedicated sending identity, grant **Send As** only for the approved support address, and enable SMTP AUTH only for that mailbox when required. Do not configure open relay or tenant-wide SMTP AUTH.
7. If an app-only mail design is required, stop and create a separate reviewed design using Exchange Online RBAC for Applications and mailbox-scoped application permissions; do not silently substitute application permissions into this delegated procedure.

For another provider, use its approved TLS-enabled IMAP service and a dedicated credential.

### 6.2 GLPI receiver

Open **Setup → Receivers** and create a receiver with:

| Setting | Value |
|---|---|
| Name | `Fluid Hose Support` |
| Address | `support@fluidhose.com` |
| Protocol | IMAP with OAuth for Microsoft 365 |
| Incoming folder | Inbox |
| Accepted archive | Provider-approved processed folder, if used |
| Refused archive | Provider-approved rejected folder, if used |

Save the receiver, test its connection and retrieve a single controlled test message.

A successfully imported message maps as follows:

- subject becomes the ticket title;
- body becomes the ticket description;
- attachments become ticket documents; and
- recognized CC addresses can become observers.

### 6.3 Routing and sender policy

Open **Administration → Rules → Rules for assigning a ticket created through a mail receiver** and create an ordered rule for the `Fluid Hose Support` receiver. At minimum, assign:

- the production Fluid Hose entity;
- the Help Desk group; and
- a default category when organisational policy requires one.

Recommended sender policy:

1. Match the sender to the email address synchronized from AD or Entra ID.
2. Accept known GLPI users.
3. Optionally accept only the known `fluidhose.com` domain.
4. Leave anonymous ticket creation disabled unless external customers must open tickets.
5. If anonymous creation is enabled, add explicit routing, spam controls and rate monitoring.

Review **Setup → Receivers → Non-imported emails** when messages are rejected. Typical causes include an unknown sender, missing destination-entity rule, auto-response headers or a sender address identical to the receiver.

### 6.4 Automatic collection

In **Setup → Automatic actions**, configure `mailgate` as **Scheduled** in **CLI** mode. Run GLPI's scheduler every minute as the web-service account:

```cron
* * * * * php /path/to/glpi/front/cron.php
```

Force a controlled collection test with:

```bash
php /path/to/glpi/front/cron.php --force mailgate
```

For container deployment, run the same command inside the GLPI application container using the image's actual GLPI installation path. Verify the path after image upgrades rather than hard-coding an unverified container path.

## 7. Configure outbound notifications

Email intake does not configure outbound mail. Under GLPI notification settings:

1. Configure authenticated SMTP using the approved mailbox or relay.
2. Set the sender and reply-to behavior so replies return to the ticket workflow without creating loops.
3. Enable the ticket-created, follow-up, assignment and resolution notifications required by policy.
4. Verify requester and technician recipients for each notification template.
5. Test SPF, DKIM and DMARC alignment for the production sender domain.

For OAuth SMTP, the authenticated account normally must be permitted to send as the configured sender or alias.

## 8. End-to-end acceptance tests

Complete these tests before production rollout:

- an approved AD/Entra user signs in and receives the intended GLPI profile;
- a disabled or removed user loses access after synchronization;
- an AD name, email or department change updates without creating a duplicate;
- a GPO-deployed GLPI Agent creates one correctly assigned computer asset;
- repeated inventory updates the same asset;
- email from a known user to `support@fluidhose.com` creates one ticket in the correct entity and group;
- the subject, body and safe test attachment are imported correctly;
- GLPI sends a ticket confirmation to the requester;
- a requester reply is attached to the existing ticket rather than opening a duplicate;
- an unauthorized or malformed message follows the documented refusal policy;
- `mailgate` continues running without an interactive GLPI session; and
- LDAP, inventory and mailbox failures generate actionable monitoring alerts;
- the selected identity path has zero queued/running SCIM or LDAP synchronization operations and every pilot event has a recorded terminal result;
- endpoint inventory has zero pending/running/retry submissions and every pilot submission has a recorded processed, failed, canceled or deliberately quarantined terminal result; and
- after a controlled email test, the GLPI `mailgate` automatic action is no longer running, no test message is stranded for retry in the receiver/mailbox processing path, and the accepted/refused disposition accounts for every submitted test message.

## 9. Operations and security

- Monitor LDAP synchronization, agent check-ins, `mailgate`, SMTP delivery and non-imported mail.
- Rotate LDAP, OAuth and SMTP credentials under change control and retest afterward.
- Never commit bind passwords, OAuth client secrets, mailbox credentials or private certificates.
- Review privileged AD group mappings at least quarterly.
- Keep GLPI, GLPI Agent and installed plugins on supported versions.
- Back up GLPI before plugin upgrades or large identity and inventory imports.
- Test local break-glass access during scheduled recovery exercises.
