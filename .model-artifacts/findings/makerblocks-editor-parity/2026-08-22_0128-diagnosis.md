# Diagnosis: MakerBlocks editor/front-end parity

## Problem

The Pricing block displays as a bordered, padded card in Gutenberg but loses its root card background, border, shadow, max-width, and padding on the front end. Descendant typography, feature, and button styles still apply.

## Reproduction

- Editor screenshot: Pricing root card styles apply.
- Front-end screenshot and `https://playground.test/`: descendant rules apply, but the first `.wp-block-makerblocks-pricing` rule does not.

## Minimized case

`build/blocks/pricing/style-index.css` begins with a UTF-8 BOM because its CSS contains the literal non-ASCII check mark used by `.makerblocks-pricing__features li::before`. Gutenberg loads the file as an external stylesheet, where the BOM is an encoding marker. WordPress front-end block-style loading inlines the file inside a `<style>` element; the BOM is then an in-document character immediately before the first selector. Only that first selector fails, explaining why descendant rules continue to work.

## Hypotheses and evidence

- Rejected: missing stylesheet. The front-end HTML contains `makerblocks-pricing-style-inline-css` and descendant pricing rules visibly apply.
- Rejected: incorrect block class. Front-end markup includes `<article class="wp-block-makerblocks-pricing">`.
- Supported: BOM-corrupted first inline selector. Front-end source contains `﻿.wp-block-makerblocks-pricing{...}` while later selectors are normal; the external editor stylesheet correctly interprets the same leading bytes as an encoding signature.

## Candidate fix-slice

Replace the literal Unicode check-mark `content` with an ASCII-only CSS-drawn check in `src/blocks/pricing/style.scss`, rebuild committed assets, and verify the built CSS no longer starts with BOM bytes (`EF BB BF`).

## Verification gaps

After rebuilding, verify the live front-end inline style starts directly with `.wp-block-makerblocks-pricing` and capture/inspect the page to confirm card parity.
